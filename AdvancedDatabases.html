Lecture 1

General Architecture of a Database Server

Core Hierarchy

Data

Raw facts with no meaning on their own. e.g. 1, ABC, 19

Record / Tuple

A row in a table — a collection of related data items that together form meaningful info.

Table / Relation

A collection of records. Columns = attributes/fields. Rows = tuples/records.

Database

A collection of related tables. Tables share common attributes that allow joining them.

DBMS

The software that manages a database — defines, stores, retrieves, and updates data efficiently.

3 Levels of Data Abstraction

LevelAlso CalledWhat It DescribesWho Uses It
PhysicalInternal SchemaHow data is actually stored on disk (bits, blocks)Storage engineers
LogicalConceptual SchemaWhat data exists and its relationshipsDBAs, developers
ViewExternal SchemaA subset of the database tailored for specific usersEnd users

Why Problems Arise Without DBMS

Data redundancy — same data stored in multiple files leads to inconsistencies.
Atomicity failure — a crash mid-transfer could deduct money from A without crediting B.
Concurrent-access anomalies — two users reading the same balance ($10,000) and both writing back only their own deduction.
Security — file systems can't easily restrict which fields different users can access.

Key Terms

Schema — the overall design/structure of the database (changes rarely).
Instance — the actual data stored at a given moment in time.
Data Independence — changing the physical schema doesn't break the logical schema or applications.
Lecture 2

Oracle Database Security

4 Security Dimensions

Physical

Servers must be in secure locations. Unauthorized physical access bypasses all software controls.

Personnel

Background checks on DBAs. Disgruntled employees are a major threat that no technical fix can fully address.

Procedural

Policies and role separation. E.g., one person handles backups, another handles reporting — never the same person.

Technical

Authentication, authorization, encryption, auditing — enforced by software and hardware.

Identity Management

As users, databases, and apps scale (e.g., 100 users × 50 databases = 5,000 potential interactions), managing access manually becomes impossible. Identity Management solves this via a centralized control system:

Single point of control = easier to secure and revoke access instantly (e.g., when an employee leaves).
Changes in one place automatically propagate to all connected databases and apps.

Security Best Practices

  • Use the principle of least privilege — users only get what they need.
  • Separate duties — one person shouldn't control both data entry and verification.
  • Enforce screen locking and desk policies for physical security.
  • Use GRANT/REVOKE in SQL to control table access per user/role.
Lecture 3

Data Blocks, Transactions & Locking

What Is a Transaction?

A transaction is a logical unit of work — a group of SQL statements that must either all succeed or all fail together.

-- Transfer $500: must be atomic
BEGIN
  UPDATE accounts SET balance = balance - 500 WHERE id = 'A';
  UPDATE accounts SET balance = balance + 500 WHERE id = 'B';
  COMMIT;   -- save both changes
EXCEPTION
  WHEN OTHERS THEN
    ROLLBACK; -- undo everything if error
END;

ACID Properties

PropertyMeaningExample
AtomicityAll or nothingTransfer either completes fully or is fully undone
ConsistencyDB stays valid before and afterAccount balances can't go negative if that's a constraint
IsolationConcurrent transactions don't interfereTwo users updating the same row see each other's committed data only
DurabilityCommitted data survives crashesAfter COMMIT, power loss doesn't lose the data

Oracle's Locking Model (Key Insight)

Readers never block writers, writers never block readers. This is fundamental to Oracle's concurrency advantage.
Row-level locking has zero extra overhead — locking 1M rows costs the same in resources as locking 1 row.
Hold locks only as long as your business logic requires. Commit when you must, not as fast as possible.
Never manually escalate row locks to table locks "for performance" — in Oracle, it wastes resources and kills concurrency.

OLTP vs OLAP Systems & Data Warehouses

OLTP vs OLAP at a Glance

FeatureOLTP (Operational)OLAP (Analytical)
PurposeDay-to-day transactionsDecision making & analysis
UsersClerks, customers, IT staffManagers, analysts, executives
DataCurrent, detailedHistorical, summarized
DB DesignEntity-Relationship (ER) modelStar / Snowflake schema
OperationsINSERT, UPDATE, DELETEMostly SELECT (read-heavy)
ScaleThousands of short transactions/secComplex queries on millions of rows

Data Warehouse — 4 Key Properties (Inmon's Definition)

Subject-Oriented

Organized around business subjects: customers, sales, products — not around applications or processes.

Integrated

Combines data from multiple heterogeneous sources (relational DBs, flat files, transaction logs) with consistent formats.

Time-Variant

Stores 5–10 years of historical data. Every record has a time element so trends can be analyzed.

Non-Volatile

Data is loaded in bulk and read — never updated record-by-record. Only two operations: load and query.

OLAP Operations on a Data Cube

  • Roll-up — summarize data to a higher level (e.g., daily → monthly → yearly sales)
  • Drill-down — go to a more detailed level (e.g., yearly → quarterly → daily)
  • Slice — filter one dimension (e.g., only show Q1 data)
  • Dice — filter multiple dimensions (e.g., Q1 AND only product category X AND only region Y)
Lecture 5

The Relational Model & SQL Standard

Core Relational Terminology

Relational TermCommon EquivalentMeaning
RelationTableA 2D structure of rows and columns
TupleRow / RecordOne entity instance
AttributeColumn / FieldOne property of the entity
DomainData typeSet of valid values for an attribute
Primary KeyPKAttribute(s) that uniquely identify each tuple
Foreign KeyFKAttribute that references the PK of another relation

Rules of Relations

No two rows in a relation can be identical.
Each cell holds exactly one value (atomicity of cells — 1NF).
Column order and row order have no meaning — a relation is a set, not a list.

Keys Example

-- Primary Key uniquely identifies each row
CREATE TABLE salesperson (
  salesperson_id  NUMBER  PRIMARY KEY,  -- PK
  name            VARCHAR2(50),
  commission_pct  NUMBER(5,2)
);

-- Foreign Key references the PK of another table
CREATE TABLE customer (
  customer_id     NUMBER  PRIMARY KEY,
  name            VARCHAR2(50),
  salesperson_id  NUMBER  REFERENCES salesperson(salesperson_id)
);

Normal Forms (Quick Reference)

1NF — each column has atomic (indivisible) values; no repeating groups.
2NF — 1NF + no partial dependencies (non-key columns depend on the whole PK).
3NF — 2NF + no transitive dependencies (non-key columns depend only on the PK, not on other non-keys).
Lecture 6

Technologies for Storing Objects in Oracle

Object-Relational Model

Oracle extends pure relational databases with object types — allowing you to store complex, structured objects directly in the DB.

Creating an Object Type

-- Define a reusable type (like a class in OOP)
CREATE TYPE address_type AS OBJECT (
  street   VARCHAR2(100),
  city     VARCHAR2(50),
  zip      VARCHAR2(10)
);

-- Use the object type as a column
CREATE TABLE employee (
  emp_id   NUMBER  PRIMARY KEY,
  name     VARCHAR2(50),
  address  address_type  -- nested object!
);

Key Advantages

Complex real-world entities (a building with multiple floors, rooms, attributes) map naturally to object types.
Enables interoperability — different applications can share the same complex data structures (critical in e.g., CAD / BIM systems).
Object types can have methods (functions/procedures defined on the type) — bringing OOP into the DB layer.

IFC Standard Context

The lecture uses IFC (Industry Foundation Classes) as a real-world example: a construction standard where architects, engineers, and managers all work with the same complex building model. Storing this in an object-relational DB allows seamless sharing across professional applications.

Lecture 7

Advanced SQL Queries (I) — Joining Tables

Types of Joins

Join TypeReturns
INNER JOINOnly rows with matching values in both tables
LEFT JOINAll rows from left table + matching rows from right (NULL if no match)
RIGHT JOINAll rows from right table + matching rows from left
FULL OUTER JOINAll rows from both tables (NULL where no match)
CROSS JOINEvery combination of rows from both tables (Cartesian product)
-- INNER JOIN: only customers with a salesperson
SELECT c.name, s.name AS salesperson
FROM customer c
INNER JOIN salesperson s ON c.salesperson_id = s.salesperson_id;

-- LEFT JOIN: all customers, salesperson may be NULL
SELECT c.name, s.name AS salesperson
FROM customer c
LEFT JOIN salesperson s ON c.salesperson_id = s.salesperson_id;

Common Table Expressions (CTEs)

A CTE names a subquery for readability and reuse. Think of it as a temporary named result set.

-- Without CTE (harder to read)
SELECT * FROM orders o
INNER JOIN (SELECT customer_id FROM customers WHERE country = 'US') us_cust
  ON o.customer_id = us_cust.customer_id;

-- With CTE (cleaner)
WITH us_customers AS (
  SELECT customer_id FROM customers WHERE country = 'US'
)
SELECT * FROM orders o
INNER JOIN us_customers uc ON o.customer_id = uc.customer_id;

Window Functions

Unlike GROUP BY (which collapses rows), window functions compute over a window of rows while keeping all rows visible.

-- Running total: see ALL orders AND cumulative sum per day
SELECT
  order_date,
  order_amount,
  SUM(order_amount) OVER (PARTITION BY order_date) AS daily_total,
  SUM(order_amount) OVER (ORDER BY order_date) AS running_total
FROM orders;
Lecture 8

Advanced SQL Queries (II) — Data Aggregation

Aggregate Functions

COUNT(*)

Number of rows in a group.

SUM(col)

Total of all values in a column.

AVG(col)

Average value (ignores NULLs).

MAX / MIN

Highest or lowest value in the group.

GROUP BY + HAVING

-- GROUP BY groups rows; HAVING filters those groups
SELECT
  department_id,
  COUNT(*) AS headcount,
  AVG(salary) AS avg_salary
FROM employees
GROUP BY department_id
HAVING AVG(salary) > 50000  -- filter AFTER aggregation
ORDER BY avg_salary DESC;
WHERE filters rows before grouping. HAVING filters groups after aggregation. Never confuse them.

ROLLUP and CUBE (Oracle Extras)

-- ROLLUP: subtotals at each grouping level
SELECT region, product, SUM(sales)
FROM sales_data
GROUP BY ROLLUP(region, product);
-- Returns: per region+product, per region, grand total

-- CUBE: all possible combinations of subtotals
GROUP BY CUBE(region, product);
-- Returns: every combination + subtotals
Lecture 9

Advanced SQL (III) — Subqueries & Parameterized Queries

Types of Subqueries

TypeReturnsOperator
ScalarSingle value (1 row, 1 col)=, >, <, etc.
Multiple-rowList of values (many rows, 1 col)IN, NOT IN, ANY, ALL
CorrelatedReferences outer query's columns; re-runs per rowEXISTS, =
Inline ViewEntire result set used as a table (in FROM)Joins, WHERE
-- Scalar subquery: employees earning above average
SELECT name, salary FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees);

-- Multiple-row: employees in departments in NY
SELECT name FROM employees
WHERE dept_id IN (SELECT id FROM departments WHERE city = 'NY');

-- Correlated: employees who earn the max in their dept
SELECT name, salary, dept_id FROM employees e1
WHERE salary = (
  SELECT MAX(salary) FROM employees e2
  WHERE e2.dept_id = e1.dept_id  -- references outer query
);

-- EXISTS: departments that have at least one employee
SELECT name FROM departments d
WHERE EXISTS (SELECT 1 FROM employees WHERE dept_id = d.id);

Parameterized Queries (Bind Variables)

Use bind variables instead of concatenating values into SQL strings — prevents SQL injection and improves performance via query plan reuse.

-- Bad: SQL injection risk, no plan caching
query = "SELECT * FROM users WHERE id = " + user_input;

-- Good: parameterized
query = "SELECT * FROM users WHERE id = :user_id";
-- Then bind :user_id = user_input separately
Lecture 10

PL/SQL — Procedural Extensions of SQL

PL/SQL Block Structure

DECLARE
  -- Variable declarations (optional)
  v_name  VARCHAR2(50);
  v_count NUMBER := 0;

BEGIN
  -- Executable statements (required)
  v_name := 'Alice';
  v_count := v_count + 1;
  DBMS_OUTPUT.PUT_LINE('Hello, ' || v_name);

EXCEPTION
  -- Error handling (optional)
  WHEN OTHERS THEN
    DBMS_OUTPUT.PUT_LINE(SQLERRM);
END;
/

Control Structures

-- IF-ELSIF-ELSE
IF score >= 90 THEN
  grade := 'A';
ELSIF score >= 80 THEN
  grade := 'B';
ELSE
  grade := 'C';
END IF;

-- LOOP variants
FOR i IN 1..10 LOOP   -- numeric for loop
  DBMS_OUTPUT.PUT_LINE(i);
END LOOP;

WHILE v_count < 5 LOOP  -- while loop
  v_count := v_count + 1;
END LOOP;

Why Use PL/SQL?

Business logic lives in the DB — reduces network round trips (1 procedure call vs. 10 SQL statements).
Reusable, stored code — compile once, run many times from any app or schema.
Tight SQL integration — can loop over query results, use SQL operators natively.
Tightly coupled to Oracle — harder to migrate to other DBMS.
Lecture 11

Functions, Procedures, Packages & Triggers

Functions vs Procedures

FunctionProcedure
Returns value?Yes (always)Optional (via OUT params)
Used in SQL?Yes (in SELECT, WHERE)No
When to useCompute and return a valuePerform an action (DML, logic)
-- FUNCTION: always returns a value
CREATE OR REPLACE FUNCTION get_annual_salary(p_emp_id IN NUMBER)
RETURN NUMBER AS
  v_monthly NUMBER;
BEGIN
  SELECT salary INTO v_monthly
  FROM employees WHERE emp_id = p_emp_id;
  RETURN v_monthly * 12;
END;

-- PROCEDURE: performs action, no mandatory return
CREATE OR REPLACE PROCEDURE give_raise(
  p_emp_id IN NUMBER,
  p_pct    IN NUMBER
) AS
BEGIN
  UPDATE employees
  SET salary = salary * (1 + p_pct/100)
  WHERE emp_id = p_emp_id;
  COMMIT;
END;

Packages

A package groups related functions, procedures, types, and variables into a named unit with two parts:

-- Package SPEC (public interface)
CREATE OR REPLACE PACKAGE emp_pkg AS
  FUNCTION  get_salary(p_id NUMBER) RETURN NUMBER;
  PROCEDURE update_salary(p_id NUMBER, p_amount NUMBER);
END emp_pkg;

-- Package BODY (implementation)
CREATE OR REPLACE PACKAGE BODY emp_pkg AS
  FUNCTION get_salary(p_id NUMBER) RETURN NUMBER AS
    v_sal NUMBER;
  BEGIN
    SELECT salary INTO v_sal FROM employees WHERE id = p_id;
    RETURN v_sal;
  END;
  -- ... other subprograms ...
END emp_pkg;

Triggers

A trigger automatically fires when a DML event occurs on a table.

-- Log whenever an employee's salary changes
CREATE OR REPLACE TRIGGER salary_audit_trg
AFTER UPDATE OF salary ON employees
FOR EACH ROW
BEGIN
  INSERT INTO salary_log (emp_id, old_sal, new_sal, changed_on)
  VALUES (:OLD.emp_id, :OLD.salary, :NEW.salary, SYSDATE);
END;
Use triggers for cross-cutting concerns (auditing, logging). Don't put core business logic in triggers — it becomes invisible and hard to debug.
Lecture 12

Anonymous Blocks & Basic PL/SQL Features

Anonymous Block vs Named Block

Anonymous BlockNamed Block (Function/Procedure)
Stored in DB?No — runs once and is goneYes — compiled and stored
Reusable?NoYes, callable by name
Use caseOne-time scripts, testingApplication logic, reuse
-- Complete anonymous block example
DECLARE
  v_emp_name  employees.name%TYPE;  -- anchored type
  v_salary    employees.salary%TYPE;
BEGIN
  SELECT name, salary
  INTO  v_emp_name, v_salary
  FROM  employees
  WHERE emp_id = 101;

  DBMS_OUTPUT.PUT_LINE(v_emp_name || ' earns ' || v_salary);
EXCEPTION
  WHEN NO_DATA_FOUND THEN
    DBMS_OUTPUT.PUT_LINE('Employee not found');
END;
/

Anchored Types

col%TYPE — declares a variable with the same type as a column. If the column type changes, the variable adapts automatically.
table%ROWTYPE — declares a record that matches the structure of an entire table row.
DECLARE
  emp_rec employees%ROWTYPE;  -- holds one entire employee row
BEGIN
  SELECT * INTO emp_rec FROM employees WHERE emp_id = 101;
  DBMS_OUTPUT.PUT_LINE(emp_rec.name);
END;
Lecture 13

Exception Handling in PL/SQL

Exception Types

Predefined Internal

Auto-raised by Oracle. Already named: NO_DATA_FOUND, TOO_MANY_ROWS, ZERO_DIVIDE, VALUE_ERROR.

Non-predefined Internal

Oracle raises them (ORA-xxxxx errors) but they don't have names. Use EXCEPTION_INIT pragma to name them.

User-Defined

Declared by you, raised explicitly with RAISE. e.g., insufficient_funds EXCEPTION;

-- Full exception handling example
DECLARE
  v_balance   NUMBER;
  insufficient_funds EXCEPTION;  -- user-defined
BEGIN
  SELECT balance INTO v_balance FROM accounts WHERE id = 1;

  IF v_balance < 100 THEN
    RAISE insufficient_funds;  -- explicit raise
  END IF;

EXCEPTION
  WHEN NO_DATA_FOUND THEN
    DBMS_OUTPUT.PUT_LINE('Account not found');
  WHEN insufficient_funds THEN
    DBMS_OUTPUT.PUT_LINE('Balance too low');
  WHEN OTHERS THEN
    DBMS_OUTPUT.PUT_LINE('Error: ' || SQLERRM);
END;

Key Predefined Exceptions

ExceptionWhen Raised
NO_DATA_FOUNDSELECT INTO returns zero rows
TOO_MANY_ROWSSELECT INTO returns more than one row
ZERO_DIVIDEDivision by zero
VALUE_ERRORConversion or size constraint violation
DUP_VAL_ON_INDEXInserting a duplicate into a unique-indexed column
OTHERSCatch-all — any unhandled exception
Use named exceptions (WHEN NO_DATA_FOUND) over WHEN OTHERS whenever possible — better precision and debugging.
In exception handlers, decide explicitly whether to COMMIT, ROLLBACK, or continue — never leave the DB in a partial state.
Lecture 14

Handling Queries with Explicit Cursors

Implicit vs Explicit Cursors

Implicit CursorExplicit Cursor
Created byOracle automaticallyYou declare it
ForAny single DML/SELECTMulti-row SELECT results
ControlVia sql%rowcount, sql%foundOPEN, FETCH, CLOSE

Implicit Cursor Attributes

BEGIN
  UPDATE employees SET salary = salary * 1.1
  WHERE dept_id = 10;

  IF SQL%FOUND THEN
    DBMS_OUTPUT.PUT_LINE('Updated: ' || SQL%ROWCOUNT || ' rows');
  ELSE
    DBMS_OUTPUT.PUT_LINE('No rows matched');
  END IF;
END;

Explicit Cursor — Full Lifecycle

DECLARE
  -- 1. DECLARE the cursor
  CURSOR emp_cur IS
    SELECT emp_id, name, salary FROM employees WHERE dept_id = 10;

  v_emp emp_cur%ROWTYPE;  -- row variable matching cursor structure
BEGIN
  OPEN emp_cur;         -- 2. OPEN: execute the query
  LOOP
    FETCH emp_cur INTO v_emp;  -- 3. FETCH: get next row
    EXIT WHEN emp_cur%NOTFOUND; -- stop when no more rows
    DBMS_OUTPUT.PUT_LINE(v_emp.name || ': ' || v_emp.salary);
  END LOOP;
  CLOSE emp_cur;        -- 4. CLOSE: free memory
END;

-- Shortcut: FOR loop cursor (auto open/fetch/close)
BEGIN
  FOR emp IN (SELECT * FROM employees WHERE dept_id = 10) LOOP
    DBMS_OUTPUT.PUT_LINE(emp.name);
  END LOOP;
END;

Cursor Attributes

%FOUND

TRUE if last FETCH returned a row.

%NOTFOUND

TRUE if last FETCH returned no row.

%ROWCOUNT

Number of rows fetched so far.

%ISOPEN

TRUE if the cursor is currently open.

The FOR loop cursor is almost always preferred — it's shorter, safer (auto-closes), and less error-prone.

OLAP: historical, read-heavy, star/snowflake, analytics

Aggregation

Functions: COUNT · SUM · AVG · MAX · MIN

Scalar → returns 1 value, use with =, >, <
